# M9 Team and 1.0

> Draft, 6 Oct 2026. Starts when M8 is merged and CI on `main` is green on Windows and macOS, and after the founder has taken the decisions in "Founder decisions needed before M9 starts". Test steps go into stage M9 of `docs/TESTING.md`. Version 0.9.0 at the start of M9; release candidates `1.0.0-rc.N`; **1.0.0 at exit**. Pipeline pack 1.0.0 (declares the app range it works with).

**Goal:** a team can share a Stratlas project, assign, discuss and approve findings, and prove later who changed what, on connected sites, on a shared folder or across an air gap with a USB stick. Sync is optional: a person alone, offline, with no account, works exactly as in 0.8, and also gains a persistent, verifiable history. The milestone ends with Stratlas 1.0: signed, in the Store, notarised, with documented upgrade paths, a support policy and a performance pass.

## Global constraints (principles)

- **Offline first, single user, no account.**
  - Every M9 feature except server sync works with no network and no account.
  - A project that is never shared behaves as in 0.8, plus the history (decision 8).
  - The zero-network suite stays green with sharing off and in hub and exchange modes.
  - The app talks to the network only when a project is in server mode and a sync runs (by a click, or by auto-sync the person turned on). The offline-only setting blocks it.
- **Sync is optional and additive.**
  - Folder projects keep their layout (data-conventions section 2).
  - New data goes to new paths only: `journal/` and `team.json` inside the project, `team/` and `journal-cache/` in userData.
  - Older builds ignore all of them.
- **New data in new files, never inside existing records.** This is a hard finding from the code:
  - `Issue` (`packages/schema/src/annotation.ts`) is a plain `z.object`, which strips unknown keys on parse. An 0.8 build that loads and saves `issues.json` would silently drop any new issue field.
  - `ChangeReview`, `Detection` (with `DetectionOrigin`) and `BoundaryEdit` are `.strict()`. An 0.8 build would refuse the whole file.
  - So M9 adds **no field** to `Issue`, `ChangeReview`, `Detection`, `BoundaryEdit`, `ProcPart` or `NarrativeFile`. Assignments, comments, approvals, members and sign-offs exist only as journal ops and their projections.
  - Free-text fields that exist (`Issue.author`, `ChangeReview.by`, `Detection.reviewedBy`, `BoundaryEdit.author`, narrative `author`) keep receiving the display name, so old readers stay right.
- **History is append-only and tamper-evident.**
  - Ops are never edited or deleted. Redaction replaces a payload with its hash, so the chain still verifies (T1).
  - Hashes use SHA-256 over JSON canonicalised by RFC 8785 (JCS). Signatures are Ed25519 through `node:crypto`, so there is no new crypto dependency.
- **A person decides.**
  - Merging never silently discards a value. The losing value stays in history and appears in the Conflicts inbox with **Restore**.
  - Approvals are human only: the agent may comment and list work, never approve (decision 6).
  - "Resolved" keeps its M8 meaning (only proposes).
- **Never modify delivered data in place.** Packages stay read-only. A client's reply is a separate signed file, never a write into the `.aio`. Every writer stays atomic with a `.bak` file (`writeJsonAtomic`).
- **Contracts are additive.**
  - Every schema change is an optional field, a new file schema, a new channel or a new enum value. Each gets a row in `contract-changes.md`.
  - No new `ExportKind` value. An older player parsing a header with an unknown kind would refuse the package. Audit exports fall under the existing `files` and `report-pdf` kinds.
  - An 0.8 build opens an M9 project and every M9 package.
- **Secrets only in the OS vault.**
  - Device private keys and server enrolment data live in Windows Credential Manager or the macOS Keychain (`createKeyVault`; test runs use the `.isolated` service).
  - They never appear in a project folder, an exchange file, a log, a diagnostics bundle or the renderer.
- **No client data, ever.** Tests, fixtures, the demo and screenshots use seeded synthetic projects and fictional people (`*@example.com`, names such as "Rana Example" and "Omar Sample"). `check-no-client-data` is extended to journals, identity cards and exchange files.
- **Licences.**
  - No GPL or AGPL in customer builds **or in the server image**.
  - No PostGIS (GPLv2) and no MinIO (AGPLv3) in what we ship. Postgres (PostgreSQL licence), Fastify, `pg` and fast-check (MIT) and `@aws-sdk/client-s3` (Apache-2.0) are fine.
- **Heavy work off the UI thread.** Journal replay, merge, verification, hashing of binaries and bundle building run in the data utility process or a worker; the renderer only renders projections.
- **Tests.**
  - Windows stay off-screen (`STRATLAS_USER_DATA`); e2e runs with `--workers=1` locally.
  - Two-reviewer tests start two Electron instances with separate userData folders. The single-instance lock is per userData folder: `app.setPath('userData', ...)` runs before `requestSingleInstanceLock` in `main/index.ts`.
  - Server tests use a loopback server allowed through `AIO_NETWORK_GUARD_ALLOW`.
  - `pnpm check`, `pnpm test:e2e` and `uv run pytest` must be green before each merge. The new `team-server` CI job (Linux, Postgres service container) must be green for T7.

## Review focus

- **Convergence.** Any two copies that have seen the same ops show byte-identical state files and projections, whatever order the ops arrived in. Property tests prove it; reviewers look for any rule that depends on arrival order or wall-clock time.
- **Never lose a write.**
  - A crash between a journal append and the JSON write recovers on next open.
  - Two people on one shared folder never overwrite each other. Today they do: `project:writeIssues` replaces the whole file with no check.
  - A concurrent delete never silently erases someone's edit.
- **Tamper evidence.** These must all be detected and named exactly in **Verify**, while the app still opens and works:
  - an edited, removed, reordered or truncated op;
  - a device segment dropped although others reference it;
  - a copied folder that forks a chain.
- **Old builds and pipelines.** An 0.8 build and the 0.3 pipeline pack edit an M9 project without losing team data. Their edits appear in history as "changed outside Stratlas" or "Inspection pipeline (run by ...)".
- **Scale.**
  - 100,000 ops open in under 1 s extra from a snapshot.
  - Merging 10,000 incoming ops takes under 3 s in a worker.
  - A 500 GB project joins a hub with JSON first; binaries follow by policy, and nothing hashes 500 GB on the UI path.
- **Exchange files from outside.** A malformed, truncated, wrongly signed or hostile `.aiosync` gives an exact error and never crashes main. Hostile means ZIP path traversal (`../`), absolute paths, links, a zip bomb by declared sizes, or duplicate members.
- **Server security.**
  - Requests are signed per device (RFC 9421, Ed25519), there are no bearer tokens in the renderer, the fingerprint is pinned at enrolment, and role checks are server-side.
  - The ops table is append-only by database grants, and receipts are countersigned.
- **M10 seams.** Nothing in M9 assumes how licences, seats or accounts work. One `entitlements` seam answers "allowed" in every M9 build.

## Sync architectures: options, trade-offs, recommendation

All three share one core so the choice is about transport and hosting, not data model: **state files plus a signed, hash-chained per-device journal** (see Design). A "transport" moves ops and blobs between copies. One TypeScript interface, `SyncTransport` (`heads()`, `pushOps()`, `pullOps(since)`, `hasBlobs()`, `putBlob()`, `getBlob(range)`), has three implementations.

```
            records (issues.json, change/, detections/, models/, manifest, edits/, report/)
                 |  every Stratlas write                    ^  merged state written back
                 v                                          |
         journal/ops/<device>.<replica>/NNNNNN.jsonl  -->  merge engine (projection, conflicts)
                 |
   +-------------+------------------+------------------------+
   |                                |                        |
 Exchange file (.aiosync)      Hub folder (SMB/NAS)      Team server (HTTPS)       [Hosted, later]
 USB, mail, air gap            single-writer files       Postgres + blob store     same protocol
```

| Criterion                       | (a) File-based exchange first: `.aiosync` patches and bundles, plus a shared-folder hub                                                                         | (b) Self-hosted server: Docker image (Node sync API, Postgres, blob store) run on-premises | (c) Hosted cloud service run by Synapse                                                                                               |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| Infrastructure for the customer | None, or an existing file share                                                                                                                                 | A Linux host or VM with Docker, TLS, backups, updates                                      | None                                                                                                                                  |
| Air-gapped sites                | Native (USB patches and bundles)                                                                                                                                | Works inside the closed network; between networks still needs (a)                          | No; still needs (a)                                                                                                                   |
| Latency between reviewers       | Minutes (hub auto-sync) to days (USB)                                                                                                                           | Seconds to minutes                                                                         | Seconds to minutes                                                                                                                    |
| Role enforcement                | Tamper-evident only: ops beyond a role are quarantined on import, but anyone with folder write access can still edit files (seen as "changed outside Stratlas") | Enforced by the server; the store is append-only                                           | Enforced                                                                                                                              |
| Large binaries                  | Hub stores them once by hash; on a LAN, layers can stream from the share; over USB, inside bundles                                                              | Resumable range transfer, dedup across projects                                            | Same as (b), but over the internet: terabytes of COPC and video are slow and costly                                                   |
| Data residency (Kuwait, GCC)    | Never leaves the customer                                                                                                                                       | Never leaves the customer                                                                  | Needs in-country hosting per client (government and regulated sectors); Synapse becomes a data processor (DPA, security attestations) |
| Synapse operating burden        | None                                                                                                                                                            | Image builds, signing, version support, install help                                       | 24/7 operations, on-call, backups, incident response, storage cost                                                                    |
| M9 build effort                 | Medium (T1, T4, T5, T6)                                                                                                                                         | Plus one stream (T7), reusing the same protocol and zod contracts                          | (b) plus multi-tenancy, billing integration, operations tooling: a milestone of its own                                               |
| Fit with the PRD                | Fits ("optional team sync")                                                                                                                                     | Fits; it is the customer's server, not SaaS                                                | Conflicts with the PRD non-goal "a cloud SaaS or multi-tenant server"; needs a PRD change                                             |
| Fit with M10                    | The free player's reply files keep "package recipients pay nothing"                                                                                             | Enrolment can later accept M10 account tokens instead of invite codes                      | Natural home for M10 accounts and identity, but couples customer data to the licence service                                          |
| Main risks                      | SMB and cloud-drive quirks; human latency; weaker enforcement                                                                                                   | Customer IT capacity; securing an internet-facing install; supporting old server versions  | Residency, trust and procurement in GCC government; cost of storing large binaries                                                    |

**Recommendation (decision 1):**

1. **Build (a) to GA in M9.** It is the only option that serves every customer (air-gapped included), costs nothing to run, and has no residency question. The journal, merge engine and blob store it needs are also everything (b) and (c) need.
2. **Ship (b) as "Team Server (preview)"** from T7, speaking the same protocol. It is gated by decision 1 and can be cut without touching the 1.0 gates. It is the answer for GCC enterprises and ministries that want enforcement and speed but keep data on their premises, the competitive gap noted in `docs/business/2026-10-05-competitors-and-pricing.md`.
3. **Defer (c) until after M10.** Offer it only with in-country hosting per client, and never as the only way for government. When built, it is (b) operated by Synapse with multi-tenancy, sharing the M10 account issuer.

## Design

### Project layout added by M9

```
<project>/
  team.json                       aio.team/1: teamProjectId, name, createdAt, createdBy (only when shared)
  journal/
    devices/<deviceId>.json       aio.device/1: device public key, actor, name, initials, app version, certs
    ops/<chainId>/000001.jsonl    aio.op/1 lines (chainId = <deviceId>.<replicaId>), rotated at 4 MB or 10k ops;
                                  each segment's first op links to the previous segment's last hash
    checkpoints/<ms>.<counter>.<chainId>.json aio.checkpoint/1: heads of every chain, counts, Merkle root, signature
userData/
  identity.json                   aio.identity/1: actor id, name, initials, email?
  team/projects.json              per project path: replicaId, mode, hub path, server id, fetch policies, peer heads
  journal-cache/<key>/            projection snapshot, per-field clocks, blob index, conflicts (rebuildable)
  blobs/                          downloaded blobs for working copies whose binaries live on a hub or server
```

- Transport configuration is per machine (drive letters and server URLs differ), so it lives in userData, never in the project.
- Members, roles and the approval policy are journal ops, signed by an owner.

### Ops, clocks and the chain

An op (`aio.op/1`, one JSON line):

```json
{
  "v": 1,
  "id": "<sha256>",
  "chain": "d_7Q…3.r_2f…",
  "dev": "d_7Q…3",
  "act": "a_01J…",
  "seq": 42,
  "hlc": "1793520903120.0003.d_7Q…3",
  "prev": "<id of seq 41>",
  "deps": { "d_k2….r_91…": "<id>" },
  "kind": "issue.patch",
  "target": { "rec": "issue", "id": "i_…" },
  "base": "<content hash before>",
  "ph": "<sha256 of JCS(payload)>",
  "payload": { "set": { "severity": 3 } },
  "via": { "agent": { "conversation": "c1", "callId": "t9" } },
  "sig": "<Ed25519 over id>"
}
```

- **`id`** is the SHA-256 of the canonical op without `id`, `payload` and `sig`; it covers `ph`. Removing a payload (redaction by an owner, recorded as its own op) leaves the chain valid; the audit shows "redacted by X on date".
- **`prev`** links the chain. **`deps`** holds the heads of other chains this device had seen, so dropping another device's tail is detectable. **Checkpoints** are signed every 500 ops and at every exchange or sync.
- **HLC (hybrid logical clock):** milliseconds, then a counter, then the device as tiebreak. HLC orders last-writer-wins decisions, never wall time alone. A remote HLC more than 5 minutes ahead raises a "clock ahead on <device>" notice; more than 24 h ahead puts the op in the inbox before it applies.
- **Device id** = `d_` plus base32 of the SHA-256 of the public key, so it cannot be claimed with another key. **Replica id** comes from userData per project folder path, so a copied or moved folder starts a new chain instead of forking one.
- **Op kinds:**
  - issues: `issue.create`, `.patch`, `.delete`, `.restore`, `.sighting.add`, `.sighting.remove`, `.status`, `.merge`, `.recode`;
  - collaboration: `comment.add`, `.edit`, `.delete`, `.redact`; `assign.set`; `approval.add`, `.withdraw`;
  - other records: `change.review`, `detection.review`, `procmodel.part`, `manifest.entry`, `boundary.edit`, `narrative.version`;
  - binaries: `blob.add`;
  - team: `member.add`, `.role`, `.remove`, `.link`; `device.revoke`; `policy.set`; `project.share`;
  - events: `package.export`, `exchange.import`, `conflict.resolve`, `record.external`, `checkpoint`.
- **Writes:**
  - Main appends and fsyncs the op, then writes the state file atomically.
  - On open, if a state file's hash equals the pre-op base of the last op, that op is re-applied (crash recovery).
  - If the hash matches neither, the difference is recorded as `record.external` (an old build, a pipeline outside a job, a hand edit).
- **Issues stay on today's path.** The renderer's debounced `project:writeIssues` keeps sending the full list; main diffs it against the last projection to make field-level ops. The issue editor's `commit()` (`packages/annotate/src/model/editor.ts`) already knows each command's label and ids. It passes them as the new optional `commands` field, so history reads "F01 to reviewed" and not just "status changed".
- **Pipelines.**
  - Main snapshots the content hashes of writable records at `jobs:start`. At job end it diffs and records ops with `via: { pipeline, jobId, packVersion }`, signed by the device of the person who started the job.
  - The inspection pipeline already keeps unknown issue keys (it works on dicts); pytest pins this.

### Merge rules per record type (T4)

| Record                                       | Key                                                                                                                                           | Rule                                                                                                                                                                                               |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Issue fields                                 | issue id plus field (`classId` and `severityModelId` together; `title`, `note`, `severity`, `measurements`, `capture`, `track`, `resolvedIn`) | Last writer by HLC wins. Concurrent different values: Conflicts entry, other value kept with **Restore**                                                                                           |
| Issue sightings                              | issue id plus the content hash of the sighting (sightings have no id today)                                                                   | Add-wins set (observed-remove); replace is remove plus add                                                                                                                                         |
| Issue status                                 | issue id                                                                                                                                      | Last writer wins, validated against the workflow at merge time (`canTransition`). `approved` is derived from approvals when a team policy exists. Concurrent close against reopen: Conflicts entry |
| Issue create, code                           | id (random), `code`                                                                                                                           | Ids never clash. Equal `code`: the later issue (by HLC) gets the next free code (`issue.recode`), with a notice                                                                                    |
| Issue delete or merge                        | id                                                                                                                                            | A concurrent edit keeps the issue (edit wins); the inbox offers "delete again". `issue.merge` re-routes sightings added concurrently to the source issue into the target                           |
| Comments                                     | comment id                                                                                                                                    | Grow-only. Edits are versions by the author only; deletes are tombstones; redaction by an owner                                                                                                    |
| Assignment                                   | target                                                                                                                                        | Last writer wins; two different concurrent assignees: Conflicts entry                                                                                                                              |
| Approvals                                    | approval id                                                                                                                                   | Grow-only; withdrawn by the same actor. An approval counts only while the target's material content hash equals the one it signed (decision 6)                                                     |
| Change review (`change/<id>.json`)           | change set id plus item id                                                                                                                    | Last writer wins on `ChangeReview` (shape unchanged); confirm against dismiss: Conflicts entry. Two issues made from one item: inbox offers merge                                                  |
| Detection review (`detections/*.json`)       | pass file plus detection `id`                                                                                                                 | Last writer wins per reviewed field (`status`, `class`, `severity`, `geom`, `issueId`, `uncertain`, `note`). Detections without `id`: whole-pass last writer wins (known limit)                    |
| Procedural model (`models/*.procmodel.json`) | model id plus part id                                                                                                                         | Last writer wins per part field; accept against reject: Conflicts entry. The built GLB is derived: rebuilt by the deterministic C5 mesher, or carried as a blob                                    |
| Manifest                                     | layer, capture, severity model and catalogue ids                                                                                              | Last writer wins per entry field; add and remove like issues. `crs`, `origin`, `verticalDatum`: owner only, and every concurrent change is a conflict                                              |
| Boundary edits                               | pile plus epoch                                                                                                                               | Last writer wins per edit, conflict flagged                                                                                                                                                        |
| Narrative                                    | part plus version (`createdAt`, author)                                                                                                       | Grow-only; the 50-version cap keeps the newest                                                                                                                                                     |
| Agent conversations                          | none                                                                                                                                          | Not synced (personal). Approved write steps appear in history through `via.agent`                                                                                                                  |
| Pipeline outputs (change sets, records)      | file                                                                                                                                          | Registered as blobs or ops attributed to the job; a re-run is last writer wins per file                                                                                                            |

Why not a CRDT library (Automerge, Yjs): they target real-time co-editing of text (a PRD non-goal). They would replace readable JSON with binary documents and force every old reader and pipeline to change. Last-writer-wins per field with sets and a visible audit is simpler for an auditor to explain.

### Large binaries (T6)

- **Content addressed.**
  - Every binary a writer produces (import, build, pipeline) is registered as `blob.add { path, sha256, size, layer?, role: source | derived }`. `AssetRef` already allows `{ hash }`, and layers keep `{ path }`.
  - Existing projects are indexed once, when first shared: a resumable job in the data process, cached by path, size and mtime.
- **On demand.** Per-layer fetch policy per machine:
  - `always`: thumbnails, posters, small rasters;
  - `on-open`: photo review copies;
  - `on-demand`: video, COPC, PMTiles and GLB over 200 MB (the default for large files);
  - `stream`: read from the hub path on a LAN through `aio://`, no copy.
- **Missing is a normal state.** `aio://` answers a 404 with `x-aio-blob: missing <sha256> <size>`. The layer shows "Not on this computer (12.4 GB). Download", and no adapter throws.
- **Transfer.**
  - Hub: copy to a temp name, rename, verify the hash.
  - Server: HTTP range in 8 MB parts, resumable, verified.
  - Bundle: `blobs/<aa>/<sha256>` members (store mode).
  - Equal hashes are stored once per hub or server.
- Whole-file hashing only in M9. Content-defined chunking (FastCDC) is a later option if re-processed large clouds turn out common.

### Identity (T2)

- **Today:** "Your name on issues" (Settings) is free text in renderer `localStorage` key `stratlas.author`, defaulting to the OS account (`app:getInfo` `user`), max 80 characters. It is written as `Issue.author`, `ChangeReview.by`, `Detection.reviewedBy` and the narrative author. There are no initials and no stable id. The session-only per-issue audit in `editor.ts` is lost on project switch.
- **M9:**
  - An **actor**: `a_` plus a random 128-bit id, display name, **initials** (derived from the first letters of the first and last words, up to 3 letters, Arabic letters allowed, editable, unique within a team by a digit suffix), optional email. Kept in userData `identity.json` and moved from `localStorage` once.
  - A **device**: an Ed25519 key pair made with `node:crypto`. The private key is in the vault (account `device-signing`); the public key and the device record go into the project's `journal/devices/`.
  - Renderer code never signs; main stamps every op.
- **Verification ladder**, shown as a badge:
  - `self`: self-asserted;
  - `owner`: an owner's device signed a member certificate;
  - `server`: enrolled with a team server;
  - `account`: M10, linked by `member.link` with a certificate from the Synapse account issuer.
  - The actor id never changes, so M10 adds a link op and rewrites nothing.
- **Identity card** (`.aioid`): name, initials, actor, device public key, self-signed. This is how a person joins a team in file mode.
- **Profiles for testing and training:** `--profile=<name>` keeps userData in `profiles/<name>` and the vault service as `<appId>.profile.<name>`, so one PC can act as two reviewers.

- **Enforcement by mode:**
  - A project that is not shared has no roles.
  - In file and hub mode, an op from a non-member or beyond the actor's role at its HLC is **quarantined** on import: kept, not applied, and listed in the inbox.
  - The server refuses such ops with 403.
- Roles describe what a person may do in a project. M10 plans describe what the installed app can do. Both checks apply, and neither replaces the other.

### Multi-reviewer workflow (T3)

- **Statuses stay** `draft`, `reviewed`, `approved`, `closed` (`STATUS_ORDER`). With a team policy:
  - `reviewed` needs a reviewer or owner.
  - `approved` is reached when `required` distinct eligible approvals exist; with `fourEyes`, the issue's creator does not count. The status op is written by the approver whose approval completed it.
  - A material edit after approval voids the approvals and returns the status to `reviewed`, with an op. Material means class, severity, sightings, measurements and status; title and note edits are recorded but do not void (decision 6).
- **Approve, Request changes** (a comment is required), **Withdraw**.
- Approvals also apply to batch sign-offs:
  - "Change register reviewed" (target: a change set);
  - "Detection pass reviewed";
  - "Model accepted";
  - report sign-off (target `report`, bound to the content hash of the report's inputs).
- **Assign** any target (issue, change item, detection pass, model part, report) to a member, with an optional due date.
- **Comments:** threads per target, markdown-lite, links shown as text (no remote content), @mentions, optional saved view (camera and time) that flies there, and `team` or `client` visibility. RTL and Arabic text are supported.
- **My work:** Assigned to me, Mentions, Awaiting my approval, Conflicts, Quarantined. In-app only: no email or push in M9.
- **Agent:** `list_my_work` (read), `show_thread` (navigate), `add_comment` (write, needs approval), `request_approval` (write: assigns and comments). There is no approve tool.

### Audit trail (T1)

- **Every op is an audit entry.** Views:
  - **History** tab per issue, change item, detection pass and part. It replaces the session-only `ann-audit` list in `IssueDetail.tsx`.
  - **Audit** screen per project, with filters (who, what, record, time, via agent, pipeline or external).
  - **Verify**, which reports chains, signatures, gaps, forks, unsigned, external, quarantined and redacted entries.
- **Exports:**
  - `audit-csv` (UTF-8 with BOM, Arabic safe);
  - `audit-json`: signed, with every device public key and the checkpoints, verifiable by `tools/audit-verify/verify.mjs` (Node, no dependencies, published with the guide);
  - house-report sections `audit` (summary and per-issue change log appendix) and `approvals` (sign-off block).
- **Every generated report prints the audit head** (head hash, entry count, verified yes or no) in its footer. A later rewrite of history would contradict reports already delivered.
- **Packages:**
  - Working packages carry the full journal.
  - Customer packages carry only a signed audit summary unless the builder ticks "Include full history" (decision 8).
  - The player can **Verify**.
- **Retention:** never compacted. About 400 bytes per op; 100k ops is about 40 MB.

### Exchange files and hub folders (T5)

- **`.aiosync`**: ZIP64, store mode, written by the existing `@aio/project/package` writer, optional AES-256 with a passphrase.
  - Members: `aio-exchange.json` (`ExchangeHeader`, signed by the sender device), `journal/devices/*.json`, `journal/ops/<chain>/<from>-<to>.jsonl`, optional `blobs/<aa>/<sha256>`.
  - Kinds:
    - `patch`: ops since the recipient's known heads, remembered per peer, or "since a date";
    - `bundle`: ops plus the blobs the recipient lacks;
    - `reply`: from a customer package in the free player; comment and acceptance ops only, signed by a client device key made on the spot, valid only when the package header allows replies.
  - Import shows a preview first: sender, signature, counts by kind, expected conflicts, blobs and size. Applying it is atomic and idempotent (ops dedupe by id). Ops after a gap are held, with "needs changes from <device> up to #N".
- **Hub folder** (`aio-hub.json`, `projects/<teamProjectId>/...`), on SMB, a NAS, or a OneDrive or Dropbox folder.
  - Each device writes only its own **files that never change**: op chunks `ops/<chain>/<from>-<to>.jsonl` and blobs `blobs/<aa>/<sha>`, written to a temp name and renamed. So no lock is needed, and cloud-drive clients never make "conflicted copies" of them; any found are ingested and reported.
  - Presence files (`presence/<device>.json`, heartbeat) show "Rana has F03 open". They are advisory.
  - Auto-sync runs on open, after saves (debounced 10 s), every N minutes, and on focus. If the hub is unreachable, work continues locally.
- **Projects opened in place on a share** (today's habit). T5 adds compare-before-write to every JSON writer, for all projects, shared or not:
  - The writer re-reads and checks the hash it last read.
  - If the file changed, the edit is replayed on top through the merge rules and written; the person sees "F03 was changed by <name>; merged".
  - A lease file (`<file>.lock`, exclusive create, heartbeat, taken over after 2 minutes of silence) prevents two simultaneous writes.
  - For team projects, the app recommends **Work on a local copy**: the JSON and journal are local, and binaries stream from the share.

### How M9 leaves room for M10

- **One crypto stack.** Ed25519 and JCS for ops, device certificates and (in M10, L1) licence files; one shared `verify` module and public keys built into the app.
- **Actor ids are permanent.** M10 accounts link through `member.link`; a named seat maps to an actor; "up to two machines" maps to that actor's device records.
- **`entitlements.ts` seam** (`can('team.sync')`, `can('collab.approve')`, ...) answers true in M9. M10's L3 replaces the provider. Viewer mode on a lapsed licence still allows reading, pulling and **Verify** and audit exports ("never lock people out of their data").
- **Enrolment is pluggable.** The server's `IdentityProvider` uses invite codes in M9; M10 account tokens or OIDC (Entra ID) plug in later.
- **Clients pay nothing.** Reply files from the free player need no licence.
- **Sync is not the licence service.** No licence or seat logic runs on the team server. A future hosted service (c) may share the M10 account issuer, but holds customer data separately.

### Plan corrections at T0

- **Hub file name.** `stratlas-hub.json` put the temporary product name into a file format. It is `aio-hub.json` (`HUB_FILE`), like `aio-package.json` and `aio-exchange.json`.
- **Checkpoint file name.** `<hlc>.<chainId>.json` repeated the device id (about 145 characters), risking Windows path limits in deep project folders. It is `<ms>.<counter>.<chainId>.json` (`checkpointFileName`).
- **Missing contracts.** T4's `Conflict` and `QuarantineEntry`, T5's `TeamStatus` and `ProjectTeamConfig` (userData `team/projects.json`, `aio.team-config/1`) and T7's `ServerInfo` had no contract row; they are in `sync.ts`.
- **Decision 8 needed ops.** The recorded journal switch is `journal.off` and `journal.on`; owner redaction of any op is `op.redact`; `comment.redact` names the ops whose payloads go (`ops`), so Verify can accept the missing payloads.
- **History labels.** The op field list had no place for the editor's command label; `Op.label?` holds it.
- **Signature domains.** "Ed25519 over id" is now over `<domain>\n<hash>` with one domain per record kind, so an op signature can never be replayed as a checkpoint, certificate or exchange signature.
- **Forward compatibility.** Op, checkpoint and exchange schemas keep unknown keys and accept unknown kinds, and verification hashes the raw JSON, never a parser's output; otherwise a 1.1 op would fail to verify in 1.0.
- **Audit export kind.** `audit-csv` and `audit-json` map to `files` as planned, but by file name they would read as `issues-csv` and `kit-json`; they are checked by format (`exportFormatRefusal`), never by name.
- **Report sections.** Adding `audit` and `approvals` to `ReportSectionId` would have shown two empty toggles in Settings; Settings now lists `HOUSE_SECTIONS`, the sections the house report prints, and T1 and T3 add theirs there.
- **Tamper fixtures.** "Edited line" is two cases (`edited-payload`: payload hash; `edited-line`: op hash), and "redacted payload" is two (`redacted-payload`: a legitimate redaction that verifies; `payload-stripped`: a payload removed with no redaction op).
- **Open risk for T8.** `ReportContentsSettings` is strict over `ReportSectionId`, so a settings file saved by 0.9 with `audit` or `approvals` toggled would be refused by an 0.8 build on the same machine (downgrade only; project data is unaffected). T8's settings migration and rollback notes should cover it.
