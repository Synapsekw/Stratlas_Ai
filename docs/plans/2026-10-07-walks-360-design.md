# Walks: 360 video placed on the map, drawing or model

Status: design approved by the founder 2026-10-07 (approach 2: path computed from the video,
anchored by pins). Spec for review before the W1 implementation plan. Slot: its own milestone right
after M10 (founder 7 Oct); number assigned when the roadmap is next renumbered.

## Problem

Construction progress monitoring needs ground-level coverage, not just drone surveys. Site teams
walk the site with a 360 camera; tools like OpenSpace, DroneDeploy 360 Walkthrough (ex
StructionSite), HoloBuilder and Cupix turn that walk into a path on a plan with a Street-View-like
viewer: you always know where you are and which way you are looking, and you can compare the same
spot across dates. The app has the parts but not the feature:

- A `video` layer with a pose file (`aio.flight/1`), a shared player on the project clock, and a
  live position dot, footprint and heading arrow on the map (`packages/maps/src/overlays.ts`). The
  lens is `pinhole` or `ftheta`; nothing handles an equirectangular video.
- A `panoramas` layer (`PanoRef = {id, src, pos, headingDeg}`) and an inside-out sphere viewer
  (`packages/engine/src/adapters/panoramas.ts`, `panoMath.ts`).
- `plan` rasters placed in the model frame and DXF import by control points (`drawing.import`). No
  PDF import.
- COLMAP via pycolmap is the chosen photogrammetry engine (ADR 0008, M10).
- Timeline T3 already plans side-by-side panoramas, paired by position, with linked look direction.

What is missing: reading 360 camera files, computing where the camera was, placing that path on
whatever reference the project has, a world-locked 360 player tied to the map, 3D overlays on the
360, and walks as input to date compare.

Reference data: `E:\Asset Inspections\Bay Zero Construction\September\360 Video\`
(`VID_20240904_083813_00_001.insv` + `LRV_..._01_001.lrv`), an outdoor handheld walk on a
selfie stick. Same-day `Mapping Photos` and `360 Panorama` folders sit beside it.

## How the market does it

- Start pin (and usually end pin) on the plan, then walk. DroneDeploy and HoloBuilder require
  start and end at least 5 m apart and not at the same spot: the computed path is fitted to the
  pins with scale, rotation and translation.
- Image-based SLAM computes the path shape without GPS, in the cloud (OpenSpace about 15 min per
  capture).
- 360 stills kept at about 2 per second and pinned to the plan; the video is for playback.
- Side-by-side compare across dates with a locked view direction (OpenSpace "Split View").

## Decisions

1. **A walk is a `video` layer, not a new layer kind.** It gets a new lens `equirect`, a pose file
   in `aio.flight/1`, and a derived `panoramas` layer for its stills. Player, clock, map dot, path
   line and panorama compare are reused. The `equirect` lens is the only contract change (see
   Contract).
2. **Approach 2: path from the video, anchored by pins.** COLMAP SfM with the `EQUIRECTANGULAR`
   camera computes the path shape; pins fix scale, rotation and position. Approach 1 (pins only,
   position between pins by step count) is the automatic fallback, not a separate mode.
   stella_vslam stays in reserve if COLMAP cannot meet the time target on long walks.
3. **Both raw and exported input.** Raw `.insv` is the default and the app stitches it. An
   equirectangular MP4 exported from Insta360 Studio is used when given (better seams, but the
   IMU may be missing).
4. **Placing is a live TypeScript fit, not a job.** Processing takes minutes; dragging a pin
   refits instantly. The raw SfM path is never modified.
5. **Pins belong to a surface.** A pin stores the layer it was dropped on and its position in that
   layer's frame. Map images, model top views, drawing sheets and the basemap are all valid
   surfaces. A project with only a drawing works fully. Re-registering the drawing (moving it,
   adding control points, putting the project on Earth) moves the walk with it.
6. **World-locked viewing.** Each frame's orientation is cancelled, so the view stays on what you
   are looking at as the camera turns. This is what makes it feel like Street View.
7. **Overlays use the viewer's own camera.** The 360 view is a perspective crop from the sphere's
   centre, so the 3D scene rendered with the same position, direction and FOV lines up at any
   zoom. No lens model fitting. Accuracy depends on the pose, refined in three levels (pins, ICP,
   manual align).
8. **No new viewer library.** The existing three.js panorama adapter gains a video texture.
9. **Permissive licences only** (ADR 0008): pycolmap (BSD-3), telemetry-parser (MIT/Apache-2.0),
   ffmpeg used as an external program as today. No ORB-SLAM, no Insta360 SDK.

## Data model

### Layers

A walk is one `video` layer:

```ts
{
  kind: 'video',
  src,                         // playback copy, see Media
  lens: { model: 'equirect' }, // new
  flight: { src: 'walks/<id>/pose.json', startUtcMs },
  walk: WalkCalibration,       // new, optional; present on equirect videos only
  poster,
  capture?,
}
```

plus one derived `panoramas` layer (`derived: { from: <video id> }`) holding the stills. Its
`PanoRef.pos` and `headingDeg` are recomputed whenever the walk's fit changes.

### WalkCalibration

```ts
type WalkCalibration = {
  raw: AssetRef; // walks/<id>/raw-path.json: SfM path in its own frame, per still
  source: 'sfm' | 'pins-only'; // pins-only when SfM failed or was skipped
  segments: { fromT: number; toT: number }[]; // SfM model pieces; one entry when unbroken
  pins: WalkPin[];
  yawOffsetDeg: number; // manual heading correction on top of the fit
  heightM: number; // capture height above ground, default 1.7
  refine?: { kind: 'icp' | 'manual'; transform: number[]; rmsM: number; against: string };
  quality: 'good' | 'check' | 'poor' | 'unplaced';
};

type WalkPin = {
  t: number; // seconds into the video
  surface: string; // layer id the pin was dropped on (raster, mesh, basemap)
  at: [number, number]; // position in that surface's frame
};
```

### Pose file

`walks/<id>/pose.json` is a normal `aio.flight/1` file written from raw path + fit + refine:
`{t, pos, q}` per sample in the model frame. Rotation is interpolated between stills with gyro
rate data, so samples run at the playback rate, not 2 per second. Existing consumers (map dot,
heading, 3D camera marker) read it unchanged.

### Files in the project

```
walks/<id>/raw-path.json        SfM path per still, raw frame, plus segment ids
walks/<id>/imu.bin              gyro + accelerometer, float32, decimated to 200 Hz
walks/<id>/sparse.ply           SfM points, for ICP
walks/<id>/pose.json            fitted path, aio.flight/1
walks/<id>/stills/<n>.jpg       full-resolution equirect stills, about 1 m apart
media/<id>-360.mp4              playback copy (see Media)
```

## Processing: `walk.process`

New `PipelineName` `walk.process` in `python/src/aio_pipelines/walk/`. Params: `src` (one or more
files), `layer` (the video layer id), `out`.

1. **Read.** Recognise the source:
   - `.insv` with the Insta360 trailer magic: model and lens calibration from the metadata record,
     gyro and accelerometer via `telemetry-parser`. Chapter files (`_001`, `_002`, ...) with the
     same timestamp stem are joined in order.
   - MP4 with a 2:1 aspect ratio, or with spherical metadata: already equirectangular. IMU only if
     present.
   - Anything else: refused with a message naming the supported inputs.
2. **Stitch.** ffmpeg `hstack` of the two lens streams into `v360` dual fisheye to equirect,
   field of view from the lens calibration (195° default). Skipped for MP4 input.
3. **Playback copy.** 3840×1920 H.264, keyframe every 0.5 s, through the existing ffmpeg proxy
   path in Electron main (`ffmpegProxy` and its encoder choice).
4. **Stills.** About one per 0.5 s while walking; stills while standing (from accelerometer step
   cadence) are dropped except the first and last of each stop.
5. **Path.** pycolmap: SIFT on half-size stills (1920×960), bottom-quarter mask (configurable),
   sequential matching, one shared `EQUIRECTANGULAR` camera with no refinement. Long walks run in
   overlapping chunks and are joined. Output: per-still position and orientation, segments, sparse
   points.
6. **Fallback.** If fewer than 60 % of stills register, `source: 'pins-only'`: positions come from
   pins later, interpolated by step count; orientation from the integrated gyro.
7. **Map stills.** Full-resolution stills picked about 1 m apart along the path go to
   `walks/<id>/stills/`.

The walk is playable after step 3; path and stills follow with job progress.

**Time target:** a 15-minute walk in 30 minutes or less on a laptop CPU with no GPU. Probe
baseline is about 6× real time; the half-size stills, standing-still skipping and chunking are
expected to cover the gap. W2 benchmarks this first. If it is missed, try COLMAP's global mapper
before considering stella_vslam.

## Placing a walk

After processing, the walk shows under its date with a **Needs placing** badge. **Place walk**
opens a split: 360 player on one side, a surface on the other, chosen in a **Place on** picker
(map image, model top view, drawing sheet or basemap of that date).

1. **Start.** The video jumps to the first walking moment (accelerometer). "Where are you now?" One
   click on the surface drops the start pin.
2. **End.** The video jumps to the last walking moment; one click drops the end pin. The whole
   path appears with its still dots.
3. **Correct (optional).** Scrub. **Pin here** at the current time, then click the true spot. Pins
   can be dragged; the fit updates live.
4. **Heading.** With an SfM path the heading comes from the fit. A "map north" tick in the 360
   shows it. **Align view** (click a landmark in the 360, then on the surface) or Alt-drag sets
   `yawOffsetDeg`.

### The fit

- 2 pins: a 2D similarity transform (scale, rotation, translation) of the raw path, projected onto
  the horizontal plane. The SfM up direction comes from gravity in the IMU, or from the mean camera
  down axis without IMU.
- 3 or more pins: one similarity transform per stretch between consecutive pins, blended over a
  short window at each pin so the path stays continuous. Each pin shows how far the path was off
  before the pin was added.
- A broken path (several segments): each segment needs at least one pin. Until it has one, its
  position is interpolated by time from its neighbours and the badge says "Path broken
  3:12-3:20, add a pin after the gap".
- Pins-only: position is interpolated between pins by step count.
- Height: the ground under the path (from the date's mesh, terrain or DSM; 0 on a flat drawing)
  plus `heightM`.
- Drawings without a true scale: the walk displays correctly on the sheet; distances are marked
  "not to scale".

Quality badge: `good` when pin residuals are under 0.5 m and every segment is pinned, `check`
under 2 m, `poor` above, `unplaced` with fewer than two pins.

### PDF drawings

New import: PDF page to `plan` raster (`format: 'image'`, placed by corners like any plain image).
Pick a page, render it at a chosen DPI, place it. The renderer is a W2 plan decision: pdf.js in
the renderer, or a permissively licensed Python renderer, but not MuPDF (AGPL).

## Viewer

Walk view: 360 player beside the map or drawing.

- On the surface: path line, still dots, position dot with a view cone that follows the 360 look
  direction and zoom.
- Click the path: seek to the nearest time. Click a still: seek to it.
- Movement: forward and back chevrons in the 360 along the path; arrow keys hop to the next or
  previous still; play for continuous motion.
- World-locked: the sphere is rotated by the inverse of the frame's pose orientation, so the look
  direction is held in world terms.
- Paused: if a full-resolution still is within 0.25 s, it replaces the video frame.
- 3D view: the path and a camera marker, on the same clock.
- HEVC is never needed for playback (H.264 copy), so decoder coverage is not a risk.

## Overlays

Any visible 3D layer can be drawn over the 360: GLB/BIM meshes, point clouds, reality mesh,
drawings draped in 3D.

- Rendering: the 3D scene is drawn with the 360 view's camera (pose position plus `heightM`, look
  direction, FOV), over the sphere.
- Modes: opacity slider, edges/X-ray, occlusion (the same-date reality mesh is drawn depth-only so
  it hides BIM behind real objects), point clouds with distance-scaled points and a 0.5 m near
  clip so the operator's body does not show.
- Exact when paused on a still; during playback the overlay follows the interpolated pose and may
  move slightly.

Accuracy needed for overlays: about ±10 cm and ±0.5°. Pins alone give roughly ±0.5-1 m and ±2°,
so:

1. **Pins**: rough placement (W2).
2. **ICP**: the walk's `sparse.ply`, after the pin fit, registered to the same-date point cloud or
   mesh with a 7-parameter similarity ICP. Stored in `refine` with its RMS. Main risk of the
   milestone (ground vs aerial overlap); probed as soon as M10 produces the Bay Zero September
   model.
3. **Align overlay**: 3 or more clicked pairs (360 pixel to model point) solve the pose, either
   for the whole walk or as a local correction at one still. Reuses the correspondence UI of the
   drone calibration (`calibrate.ts`).

## Compare (W5)

Walk stills are a `panoramas` layer per date, so Timeline T3 compares them like any panorama set.

- Pairing: nearest still on the other date within 3 m; otherwise "Nearest capture 7.4 m away" with
  a jump button.
- Look direction linked in world terms (both sides are world-locked).
- Walks and drone 360 panoramas mix. Overlays can be on in both panes. Stepping in one pane moves
  the other to its nearest still.

## Failures

| Case                                                          | Behaviour                                                          |
| ------------------------------------------------------------- | ------------------------------------------------------------------ |
| SfM registers under 60 % of stills                            | `pins-only`, badge says so and asks for pins at corners            |
| SfM splits into several models                                | segments kept, badge names the gap and asks for a pin after it     |
| No IMU (Studio export without metadata)                       | SfM only; up direction from cameras; slightly less smooth rotation |
| Chapter files                                                 | joined by name                                                     |
| GoPro Max `.360`, Ricoh Theta raw, Insta360 X2 two-file clips | refused with the list of supported inputs (phase 2)                |
| ffmpeg missing or cannot decode HEVC                          | existing ffmpeg detection, clear refusal                           |
| Pin on a surface that is later deleted                        | pin kept but inactive; badge drops to `check` or `unplaced`        |

## Contract

- `lens.model: 'equirect'` and the optional `walk` field on `video` layers. Older 1.x builds must
  not crash on them. W1 first checks how shipped builds parse a `video` layer with an unknown lens
  model and an unknown field. If they reject the layer or the project, decision 1 flips: walks
  become a new layer kind `walk` with the same fields, which shipped builds already keep as an
  `OpaqueLayer`. Recorded in `contract-changes.md` either way.
- `PipelineName` `walk.process` with its params schema.
- New project folder `walks/<id>/` in `data-conventions.md`.

## Testing

- **Synthetic ground truth (accuracy gate).** Render a known GLB scene into equirect frames along a
  known path with known orientation, encode as video, run `walk.process`, pin start and end, run
  ICP against the source mesh. Assert path error under 0.10 m and heading under 0.5° after refine.
- **Unit:** similarity and piecewise fit, segment handling, pins on drawing surfaces and their
  re-registration, world-locked rotation, quality badge rules, stills selection.
- **Trailer reader:** a small extracted `.insv` trailer fixture (metadata + a few hundred IMU
  samples), not the full video.
- **Pipeline:** a 10 s cut of the Bay Zero walk; runs locally when the file is present, skipped in
  CI.
- **e2e (off-screen, `STRATLAS_USER_DATA`):** load a pre-processed walk fixture, place two pins,
  check dot and cone follow the clock, click-to-seek, toggle an overlay, compare across dates.
- **Field check:** Bay Zero September walk on the September map image; error at identifiable
  landmarks.
