# Tracks across survey dates (Wave 3 M2)

## What changed

- **Tracks, derived at read time** (`packages/change/src/tracks.ts`, exported from `@aio/change/core`): the same antenna, change region or thermal hot spot seen on several survey dates is linked into one track, with a trend per value (antenna azimuth, downtilt and centre height; region area, net volume and largest distance; hot spot peak and ΔT). Linking runs date by date, oldest first, best pair first, each sighting used once, so the same files always give the same tracks. Nothing about tracks is stored.
- **Matching rules.** Antennas: the same unit id first (the re-run merge already keeps ids across dates), else the same kind within `max(0.3 m, half the face)`. Hot spots: placed ones (multi-view `vote.point`) within `max(0.5 m, 10 x the ground sample distance)`, the distance worked out from the photo's position and lens. Change regions: regions of consecutive pairs whose outlines overlap 30 % or whose centres lie within `max(1 m, 3 x the set's cell)`. Positions are compared lined up. Rejected units and hot spots and dismissed regions are left out; drafts are marked.
- **What each date measured** (the one store): `telecom.antennas` also writes `telecom/history/<captureId>.json` (`aio.antenna-history/1`) on commit, one entry per unit the run fitted with that run's own fit (centre, extents, azimuth, downtilt), never the inventory's merged values: the merge keeps an accepted unit's old geometry when the new fit has less support, keeps units a person owns and carries units it did not find. `reviewed` is false for a status carried over from an earlier date; the replaced date's record takes the statuses the person changed while it was live, and a run on a date that already has a record keeps its reviewed entries. New IPC `telecom:readAntennaHistory` (deleted units left out). Contract row and data-conventions section 39 line added.
- **Review fixes (12 Nov).** Line-up turns also turn azimuths; a region pair reads one set per producer (the newest whole-site one that is not out of date, else per area), in the Changes panel and the digest alike; no "since the date before" for a value the latest date lacks; no height fallback to the absolute box centre; the antenna card says that tracks need processing tools 0.35.0 when the live date has no record.
- **Where it shows.** An "Across survey dates" table (`TrackHistory`) in the antenna details card, under a selected hot spot in Inspect, and in a change region's detail in the Changes panel. Nothing shows for an object seen on one date.
- **Site digest.** Three rules in `@aio/insights` (`trackRules.ts`): an antenna turned 3 degrees or more in azimuth or 1 degree in downtilt (warning), a hot spot's peak rose 5 °C or more (warning), a change region grew 20 % and 5 m² or more (info). Each speaks only about the latest survey date; antennas and hot spots only when both dates are reviewed. New actions Show antenna and Open in Inspect.
- Pipeline pack 0.35.0, in its own commit (this is the batch's first Python change).

## Decisions

- Tracks are derived, not stored; only the antenna records are new on disk, because nothing else kept what an earlier date measured.
- A date run on an older pack has no record, and the track leaves it out rather than read the merged inventory.
- Region sightings come only from consecutive pairs (a long first-to-last set would count a date twice).
- The digest ignores draft antennas and hot spots: a trend between unreviewed drafts would be noise. An accepted antenna a later run measured again counts as confirmed on that date (coordinator, 12 Nov): the person accepted it, and the fit is new data.
- A replaced date without a record (an older pack) gets one from its inventory's stored values, so upgrading does not lose it.
- No agent read tool: the fact index (M1) is being built in parallel and will be the query layer.
- Values in the track table are shown in metres, degrees and °C, not converted to the site's units yet.

## How to test

1. Open a project with two survey dates. Detect antennas on the first date's cloud with pipeline pack 0.35.0 and accept them, then detect again on the second date's cloud (no need to accept them again). In Project > In this project, pick an antenna. Its details card shows "Across survey dates" with one row per date, the azimuth and downtilt each date measured, no "(draft)" on the second date, and "Since the date before" with the change (for example "+8.0°"), even where the inventory kept the earlier fit. Backed by `apps/desktop/e2e/site-tracks.spec.ts` (first case; records written by the fixture, the acceptance carried over), `test_each_date_keeps_a_copy_of_its_inventory` in `python/tests/test_telecom_pipeline.py` (the real job writing both records) and `test_the_record_holds_this_runs_fit_not_the_kept_geometry` and `test_an_accepted_unit_measured_again_keeps_accepted_with_the_new_fit` in `python/tests/test_telecom_history.py`.
2. With that antenna turned 3 degrees or more between the dates, the Site digest at the top of the Project tab shows "Antenna P1 turned 8.0° in azimuth since ...". Backed by `site-tracks.spec.ts` (first case) and the digest case in `apps/desktop/src/renderer/tracks/siteTracks.test.ts`.
3. A project whose first date was detected with an older pack keeps that date: after the first 0.35.0 detection on the second date, the antenna card lists both dates. Backed by `test_a_replaced_date_without_a_record_gets_one_from_its_inventory` in `python/tests/test_telecom_history.py`.
4. On a project whose latest detection ran on an older pack, the antenna card says that following it across dates needs processing tools 0.35.0. Backed by `site-tracks.spec.ts` (second case).
5. Hot spots and change regions: covered by unit tests only (`packages/change/src/tracks.test.ts`, `apps/desktop/src/renderer/tracks/siteTracks.test.ts`, `packages/insights/src/trackRules.test.ts`); no demo project has thermal photos or change sets on three dates yet, so there is no step to click through.

## Open threads

- The digest is shown only when two dates each hold a layer (`canCompare` in `panelData.ts`), while `SiteDigest` itself needs only two captures; a project whose layers are not filed per date shows no digest, so no track insight either. Existing behaviour, left as it is.
- Track values are not converted to imperial site units.
- A hot spot and a change region e2e need a two-date thermal fixture and a three-date change demo.
- The digest only knows antennas and hot spots once their stores have loaded for the project.
