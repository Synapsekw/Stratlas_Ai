# Tracks across survey dates (Wave 3 M2)

## What changed

- **Tracks, derived at read time** (`packages/change/src/tracks.ts`, exported from `@aio/change/core`): the same antenna, change region or thermal hot spot seen on several survey dates is linked into one track, with a trend per value (antenna azimuth, downtilt and centre height; region area, net volume and largest distance; hot spot peak and ΔT). Linking runs date by date, oldest first, best pair first, each sighting used once, so the same files always give the same tracks. Nothing about tracks is stored.
- **Matching rules.** Antennas: the same unit id first (the re-run merge already keeps ids across dates), else the same kind within `max(0.3 m, half the face)`. Hot spots: placed ones (multi-view `vote.point`) within `max(0.5 m, 10 x the ground sample distance)`, the distance worked out from the photo's position and lens. Change regions: regions of consecutive pairs whose outlines overlap 30 % or whose centres lie within `max(1 m, 3 x the set's cell)`. Positions are compared lined up. Rejected units and hot spots and dismissed regions are left out; drafts are marked.
- **Per-date antenna copies** (the one store): `telecom.antennas` also writes `telecom/history/<captureId>.json` on commit, the inventory it replaces when that names another date (as the person reviewed it) and its own, without crops. The live inventory already held only one date, so an earlier azimuth was lost on every new run. New IPC `telecom:readAntennaHistory`. Contract row and data-conventions section 39 line added.
- **Where it shows.** An "Across survey dates" table (`TrackHistory`) in the antenna details card, under a selected hot spot in Inspect, and in a change region's detail in the Changes panel. Nothing shows for an object seen on one date.
- **Site digest.** Three rules in `@aio/insights` (`trackRules.ts`): an antenna turned 3 degrees or more in azimuth or 1 degree in downtilt (warning), a hot spot's peak rose 5 °C or more (warning), a change region grew 20 % and 5 m² or more (info). Each speaks only about the latest survey date; antennas and hot spots only when both dates are reviewed. New actions Show antenna and Open in Inspect.
- Pipeline pack 0.35.0, in its own commit (this is the batch's first Python change).

## Decisions

- Tracks are derived, not stored; only the antenna copies are new on disk, because nothing else kept an earlier date's antenna values.
- Region sightings come only from consecutive pairs (a long first-to-last set would count a date twice).
- The digest ignores draft antennas and hot spots: a trend between unreviewed drafts would be noise.
- No agent read tool: the fact index (M1) is being built in parallel and will be the query layer.
- Values in the track table are shown in metres, degrees and °C, not converted to the site's units yet.

## How to test

1. Open a project with two survey dates and an antenna inventory where one antenna was measured on both dates (detect antennas on the first date's cloud, accept them, then detect again on the second date's cloud with pipeline pack 0.35.0). In Project > In this project, pick that antenna. Its details card shows "Across survey dates" with one row per date, the azimuth and downtilt on each, and "Since the date before" with the change (for example "+8.0°"). Backed by `apps/desktop/e2e/site-tracks.spec.ts` (inventory and copy written by the fixture) and `test_each_date_keeps_a_copy_of_its_inventory` in `python/tests/test_telecom_pipeline.py` (the real job writing both copies).
2. With that antenna turned 3 degrees or more between the dates, the Site digest at the top of the Project tab shows "Antenna P1 turned 8.0° in azimuth since ...". Backed by `site-tracks.spec.ts`.
3. Hot spots and change regions: covered by unit tests only (`packages/change/src/tracks.test.ts`, `apps/desktop/src/renderer/tracks/siteTracks.test.ts`, `packages/insights/src/trackRules.test.ts`); no demo project has thermal photos or change sets on three dates yet, so there is no step to click through.

## Open threads

- The digest is shown only when two dates each hold a layer (`canCompare` in `panelData.ts`), while `SiteDigest` itself needs only two captures; a project whose layers are not filed per date shows no digest, so no track insight either. Existing behaviour, left as it is.
- Track values are not converted to imperial site units.
- A hot spot and a change region e2e need a two-date thermal fixture and a three-date change demo.
- The digest only knows antennas and hot spots once their stores have loaded for the project.
