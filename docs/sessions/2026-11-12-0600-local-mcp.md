# Local MCP server (outside agents read the open project)

## What changed

- This PR adds a local MCP server (intelligence review Wave 3, X1; study `research.md` section 3; founder decision 5: local only, read-only first, the same tool registry as the agent).
- Tools come from the agent's own specs (`packages/ai/src/mcp-tools.ts`).
  - `MCP_TOOL_CLASS` classifies every read tool. A tool is offered only with a reviewed `pure` note that says what it reads; every other tool has `exclude` and a reason. `mcpToolList()` builds the MCP list from `allToolSpecs()` (name, description, JSON Schema of the zod input), so it cannot drift.
  - The parity tests fail when the agent gains a read tool that is not classified, when an exposed tool has no purity note, or when a tool that is not `risk: 'read'` (or whose risk depends on its input, `run_action`) would be exposed.
  - 24 tools are offered, `query_facts` and `history_of` among them. Image results are dropped: no imagery leaves the app through MCP.
- The server (`packages/ai/src/mcp-server.ts`, entry `@aio/ai/mcp`, main only) uses the official MCP TypeScript SDK 1.32.2 (Streamable HTTP, one session per client).
  - It listens on 127.0.0.1 and nowhere else.
  - Every request needs `Authorization: Bearer <token>` (compared in constant time). The Host header must name the loopback address and port (DNS rebinding), and a request with a browser `Origin` is refused.
  - At most 4 tool calls run at once across all sessions; more are answered "busy".
  - Sessions are capped at 16 (the least recently seen ends) and end after 30 minutes idle, since many clients never say goodbye.
  - It knows each client's name and version from `initialize`, plus its call count. Disconnect ends one session; a new token ends them all.
- Main host (`apps/desktop/src/main/mcp.ts`):
  - It is off by default. The switch, the token, the port and the per-project choices live in `userData/mcp.json` (`aio.mcp/1`). The per-project choice is keyed by folder and project id.
  - The token is registered as a secret (never in a log or a diagnostics bundle) and never travels in a status or a broadcast. Settings asks for it with `mcp:revealToken` only when the person presses Show or Copy.
  - The token and port are kept, so a pasted setup keeps working across restarts. If the kept port is taken, the server does not move silently: Settings shows the error with "Use a new port" (`mcp:newPort`), which moves the port and makes a new token.
  - Calls go to the project opened last. The renderer runs them with the agent's own executor (`mcp:call`, answered by `mcp:result`, 30 s timeout). A call whose project changed while it ran is refused, in the renderer and again in main.
  - Switching the server off while it starts closes the server it was starting. Changes run one after another, in the order asked.
- Settings > AI providers > "Outside apps (MCP)" holds:
  - the switch with "On, 24 read-only tools";
  - the address and the token (hidden until shown), with Copy and New token;
  - copyable setups for Claude Code (`claude mcp add --transport http ...`) and Claude Desktop (`npx -y mcp-remote@0.15.2 ...`, needs Node.js). On Windows, Claude Desktop mangles an argument that holds a space, so the header value goes in an `AUTH_HEADER` environment variable, as mcp-remote's README advises;
  - the connected apps, with Disconnect;
  - a warning while offline only is on;
  - the "Let outside apps read this project" switch for the open project, with a line that says whether it is served and why.
- `aio.mcp/1` is listed in the schema versions, and the third-party notices list the SDK and the packages it brings.
- Contract change: new `@aio/schema` `mcp.ts`, IPC `mcp:*` and events `mcp:call`, `mcp:changed` (row in `docs/architecture/contract-changes.md`). No pipeline change, no pack bump.

## Purity audit of the exposed tools

A reviewer found that `list_model_parts` is not a pure read: it can save a new model, it switches the modeller view, and it shares drawing content by the in-app route instead of the drawing consent. Every tool that was exposed was then audited executor by executor (the packages/ai executors and the app-side ones in `modeller/`, `engineer/` and `agent/`).

- **Excluded:**
  - `list_model_parts`, for the reasons above.
  - `list_components`: drawing-derived engineering model content with no consent check.
  - `list_model_corrections`: drawing-derived, and its consent is decided on the in-app route, which an outside app is not.
  - `list_changes` and `compare_captures`: they read change sets through main's `change:read`, which refreshes the compare-before-write record that a later review save relies on.
  - `list_sites`: it spans every project of the library.
  - Drawing-derived content is therefore never served over MCP. A tool that brings it back needs an MCP check against `aiCloudDrawings` (and the scan and photo consents), whatever the in-app route.
- **Pure (24):** `list_layers`, `list_clips`, `find_clips_near`, `find_places`, `list_issues`, `summarize_issues`, `measure_distance`, `summarize_by_zone`, `summarize_by_class`, `find_issues_near`, `list_my_work`, `list_assets`, `accuracy_summary`, `list_measurements`, `get_volume`, `rank_locations`, `query_facts`, `history_of`, `list_surveys`, `list_detections`, `list_jobs`, `thermal_summary`, `list_walks` and `list_actions`.
  - None of them writes, changes the view, selection or screen, or starts a job, capture or network call. Their fetches are `aio://project` reads of the open project.
  - Some walk the scene into an in-memory cache. `find_clips_near` reads every flight log on each call, and the in-flight cap bounds that.
  - `list_issues`, `rank_locations`, `list_clips` and `list_surveys` answer relative to what is selected or focused in the app.
  - Layer names, including a `plan` raster's name, stay visible through `list_layers` and `find_places`, as they are to the in-app agent.

## Decisions made on the founder's behalf

- **Streamable HTTP on 127.0.0.1, no stdio launcher.** The packaged app has the Electron `runAsNode` fuse off, so a launcher that runs on the app's own Node cannot ship without weakening a security fuse. A second Electron instance as a stdio bridge would fight the single-instance lock and start slowly. Claude Code and most clients speak HTTP with headers; Claude Desktop goes through `mcp-remote`.
- **A kept bearer token, rotated on demand**, not a new one per app start. It keeps the setup pasted into Claude Code valid. The token lives in the person's own profile, which other Windows users cannot read. "New token" rotates it and disconnects everyone.
- **Privacy (coordinator's call, 12 Nov):**
  - A project is served only once the person turns on "Let outside apps read this project" for it. Cloud AI being on does not serve it.
  - A package or manifest that forbids cloud AI is never served.
  - While offline only is on, every call is refused, because outside clients usually pass what they read to a cloud model.
- **mcp-remote 0.15.2**, the newest release at least two weeks old on 12 Nov 2026, pinned so a later release cannot change what the pasted setup starts.
- **The open project only.** No project id parameter: the server answers for the project open in the app window, with the same executors the in-app agent uses.

## How to test

Every step is backed by `apps/desktop/e2e/mcp-server.spec.ts` (run the CI way above), unless it says otherwise.

1. Open the quarry survey demo and let "Search this project" in the Project tab say how much it indexed. Go to Settings > AI providers and scroll to "Outside apps (MCP)". The switch is off. Turn it on: the line says "On, 24 read-only tools", and an address `http://127.0.0.1:<port>/mcp` and a hidden token appear. Show reveals the token. The Claude Code setup line names the address.
2. Connect an MCP client with the address and token (the spec uses the MCP TypeScript SDK's client). It lists the tools: `query_facts`, `history_of` and `list_issues` are there, and no write, camera or capture tool is. A request without the token gets 401.
3. Even with cloud AI on, ask the client to search the project: it is refused with "not shared with outside apps". Settings shows "Not served".
4. Turn on "Let outside apps read this project". The line says "Served: you let outside apps read this project". Ask again for "Stockpile SP1": the answer lists the pile's facts from the fact index. `list_model_parts` and a write tool such as `create_issue_draft` are refused.
5. Turn on offline only: the same search is refused with "offline only". Turn it off again.
6. Under "Connected apps" the client shows with its name, version and call count. Disconnect it: the list says "No app is connected." and the client's next request fails.
7. Press New token: the token hides again, the old one is refused, and Show gives a new one that connects. Turn the switch off: the port closes.

"Use a new port" (a kept port taken by another program) is backed by `main/mcp.test.ts`, not the e2e spec. To use the server from Claude Code, paste the Copy of the Claude Code setup into a terminal (`claude mcp add --transport http ...`). That command was not run against the app in this PR: the spec uses the SDK client, which speaks the same Streamable HTTP with the same header.

## Open points

- A native stdio launcher (for clients without HTTP and without Node.js) would need a small signed helper exe; not built.
- The engineering model tools and the change tools could come back with an MCP-specific drawing consent check and a read path that leaves the compare-before-write record alone.
- Write tools over MCP (with an in-app approval) are a later step, if wanted.
- The agent's offline branch (A3) may add read tools: the parity test will then ask for their classification, with a purity note, when they meet.
