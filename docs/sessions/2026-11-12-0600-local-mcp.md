# Local MCP server (outside agents read the open project)

## What changed

- This PR adds a local MCP server (intelligence review Wave 3, X1; study `research.md` section 3; founder decision 5: local only, read-only first, the same tool registry as the agent).
- Tools come from the agent's own specs (`packages/ai/src/mcp-tools.ts`).
  - `MCP_TOOL_CLASS` classifies every read tool, `expose` or `exclude` with a reason. `mcpToolList()` builds the MCP list from `allToolSpecs()`: name, description, and the JSON Schema of the zod input, so it cannot drift.
  - A parity test fails when the agent gains a read tool that is not classified, or when a tool that is not `risk: 'read'` (or whose risk depends on its input, `run_action`) would be exposed.
  - 29 tools are offered, `query_facts` and `history_of` among them. `list_sites` is excluded: it spans every project of the library, whose privacy settings differ.
  - Image results are dropped: no imagery leaves the app through MCP.
- The server (`packages/ai/src/mcp-server.ts`, entry `@aio/ai/mcp`, main only) uses the official MCP TypeScript SDK 1.32.2 (Streamable HTTP, one session per client).
  - It listens on 127.0.0.1 and nowhere else.
  - Every request needs `Authorization: Bearer <token>` (compared in constant time). The Host header must name the loopback address and port (DNS rebinding), and a request with a browser `Origin` is refused.
  - It knows each client's name and version from `initialize`, plus its call count. Disconnect ends one session; a new token ends them all.
- Main host (`apps/desktop/src/main/mcp.ts`):
  - It is off by default.
  - The switch, the token, the port and the per-project choices live in `userData/mcp.json`. The token and port are kept, so a pasted setup keeps working across restarts; a taken port falls back to a free one.
  - Calls go to the project opened last, and the renderer runs them with the agent's own executor (`mcp:call`, answered by `mcp:result`, 30 s timeout). The renderer refuses when another project is open by then.
- Renderer: `agent/mcpBridge.ts` runs `runRendererTool` with the agent's default tool context (the 3D view's window) for MCP tools only.
- Settings > AI providers > "Outside apps (MCP)" holds:
  - the switch;
  - the address and the token (hidden until shown), with Copy and New token;
  - copyable setups for Claude Code (`claude mcp add --transport http ...`) and Claude Desktop (`npx mcp-remote ...`, needs Node.js);
  - the connected apps, with Disconnect;
  - the "Let outside apps read this project" switch for the open project, with a line that says whether it is served and why.
- After the independent review:
  - Switching the server off while it starts closes the server it was starting, and a token or project choice made meanwhile is kept.
  - A call whose project changed while it ran is refused, in the renderer and again in main, so one project's data never goes out under another project's gate.
  - Sessions are capped at 16 (the least recently seen ends) and end after 30 minutes idle, since many clients never say goodbye.
  - The status event skips a closed window.
- `aio.mcp/1` is listed in the schema versions, and the third-party notices list the SDK and the packages it brings.
- Contract change: new `@aio/schema` `mcp.ts`, IPC `mcp:*` and events `mcp:call`, `mcp:changed` (row in `docs/architecture/contract-changes.md`). No pipeline change, no pack bump.

## Decisions made on the founder's behalf

- **Streamable HTTP on 127.0.0.1, no stdio launcher.** The packaged app has the Electron `runAsNode` fuse off, so a launcher that runs on the app's own Node cannot ship without weakening a security fuse. A second Electron instance as a stdio bridge would fight the single-instance lock and start slowly. Claude Code and most clients speak HTTP with headers; Claude Desktop goes through `mcp-remote`.
- **A kept bearer token, rotated on demand**, not a new one per app start. It keeps the setup pasted into Claude Code valid. The token lives in the person's own profile, which other Windows users cannot read. "New token" rotates it and disconnects everyone.
- **Privacy: an outside agent is treated like a cloud provider.** The open project is served when cloud AI could read it (cloud AI on, offline-only off, the policy allows), or when the person lets outside apps read that project. A package or manifest that forbids cloud AI is never served, whatever the switch says: that is the builder's call, not the reader's.
- **The open project only.** No project id parameter: the server answers for the project open in the app window, with the same executors the in-app agent uses.

## How to test

Every step is backed by `apps/desktop/e2e/mcp-server.spec.ts` (run the CI way above), unless it says otherwise.

1. Open the quarry survey demo and let "Search this project" in the Project tab say how much it indexed. Go to Settings > AI providers and scroll to "Outside apps (MCP)". The switch is off. Turn it on: the line says "On, 29 read-only tools", and an address `http://127.0.0.1:<port>/mcp` and a hidden token appear. Show reveals the token. The Claude Code setup line names the address.
2. Connect an MCP client with the address and token (the spec uses the MCP TypeScript SDK's client). It lists the tools: `query_facts`, `history_of` and `list_issues` are there, and no write, camera or capture tool is. A request without the token gets 401.
3. With cloud AI off, ask the client to search the project: it is refused with "not shared with outside apps". Settings shows "Not served".
4. Turn on "Let outside apps read this project". The line says "Served: you let outside apps read this project". Ask again for "Stockpile SP1": the answer lists the pile's facts from the fact index. A write tool such as `create_issue_draft` is still refused.
5. Under "Connected apps" the client shows with its name, version and call count. Disconnect it: the list says "No app is connected." and the client's next request fails.
6. Press New token: the token changes, the old one is refused and the new one connects. Turn the switch off: the port closes.

To use it from Claude Code, paste the Copy of the Claude Code setup into a terminal (`claude mcp add --transport http ...`). That command was not run against the app in this PR: the spec uses the SDK client, which speaks the same Streamable HTTP with the same header.
