# ADR 0003: Updates, release notes and rollback

- Status: Accepted, 2026-10-05
- Deciders: lead engineer (M7 stream D1); founder to confirm

## Context

M7 needs updates customers can trust on offline workstations: install from a file, an optional online check that is off by default, release notes, and a way back when a new version fails. The review focus is strict: an update interrupted by power loss, a dropped network or a quit must never leave an install that will not start, and the previous version must stay runnable.

Until now the online check used electron-updater (`generic` provider, `latest.yml`). electron-updater runs the new NSIS installer over the installed folder and deletes its cache afterwards. electron-builder's NSIS template moves the old files to `%TEMP%\nsX.tmp\old-install` and restores them only when a file is busy; after a power cut in the middle of the extraction the install folder is half old, half new or empty, and nothing on the machine can start the app again. electron-updater has no notion of a previous version.

## Decision

1. **Own small updater, no electron-updater.** The feed is one static JSON file, `stratlas-update.json` (`aio.update-feed/1` in `@aio/schema` `update.ts`): `version`, `releasedAt`, `notes` (Markdown) and per platform (`win-x64`, `win-arm64`, `mac-arm64`, `mac-x64`) the installer `url` (relative to the feed or absolute http(s)), `sha256` and `size`. `tools/release/feed.mjs` writes it next to the installers at the end of `dist.mjs`, so any folder on a web server, share or USB stick can serve a release. The address is a Setting (`updateUrl`, the `.json` file or its folder). Requests go through the `stratlas-updates` session only when the person presses **Check now** or **Download and install**; the switch is off by default and disabled on an offline-only workstation. Store copies never use it.
2. **Download**: to `<userData>/updates/downloads/<name>.partial`, resumed with an HTTP `Range` request after an interruption (a server that ignores ranges starts over), at most `size` bytes, synced to disk, and renamed to its final name only when size and SHA-256 match the feed. On Windows the file then passes the same check as an installer picked from a file: valid Authenticode signature from the publisher and exactly the version the feed announced. On macOS the DMG is not signed by electron-builder; the feed's SHA-256 over the chosen transport and Gatekeeper's check of the notarised app on first start apply.
3. **Publisher identity**: `brand.json` may carry `signing.windowsPublisher`, the exact CN (or O) of the code-signing certificate stream D2 configures. When present the signer must equal it; when absent the CN or O must contain `brand.company` (the previous behaviour, now limited to CN and O).
4. **Rollback by keeping the running version, not its installer.** Right before any installer runs (file or feed), the running app copies its own installed folder (Windows, `dirname(execPath)`) or `.app` bundle (macOS) to `<userData>/updates/previous/<version>/`, through `original-fs` so `app.asar` stays a file. The copy goes to `<version>.partial` and is renamed when complete. Only one previous version is kept (about 400 MB). If the copy fails, the update does not start. On Windows a Start-menu entry "Stratlas <version> (previous version)" points at the kept copy until the new version has started well. Development, portable and Store copies cannot keep a copy and say so.
   - Why not the previous installer: the app never has its own installer (it may have been installed by hand or by IT), and re-running an older NSIS installer goes through the same non-atomic extraction. A kept copy is runnable as is, even with the install folder destroyed.
5. **Journal** `<userData>/updates/journal.json` (`aio.update-journal/1`, main-only, written to a temporary file and renamed): `pending` (`from`, `to`, `appRoot`, `launches`, `failures`, `cleanExit`, `declined`), `previous` (`version`, `dir`, `exe`, `appRoot`) and the last `rolledBack`.
6. **First-start watch**: each start of `pending.to` counts a launch before any window opens. The renderer calls `app:rendererReady` once settings and the library have loaded; that closes `pending` (the kept copy stays for a later manual return). A failure is a start that ended without ready and without a normal quit (crash, hang killed by the person, power cut), no ready within 90 s, or the window's renderer crashing twice (the first crash reloads it). On a failure, now or at the next start, a native dialog (it does not depend on the renderer) offers **Return to <previous>** or **Keep <new>**; keeping stops the questions for that update. A quit before ready is not a failure. A start of `pending.from` means the installer did not finish: the record and the now-redundant copy are removed.
7. **Restore**: the newer version starts the kept copy with `--stratlas-restore-into=<appRoot> --stratlas-restore-wait=<pid> --stratlas-restore-from=<version>` and quits. These arguments are a stable contract between versions. The kept copy (outside the single-instance lock) waits for that process to exit, copies itself to `<appRoot>.restoring`, renames `<appRoot>` to `<appRoot>.failed` (retrying while a scanner holds a file), renames `.restoring` to `<appRoot>`, deletes `.failed`, records `rolledBack`, starts the restored app and exits. The installed folder is replaced by two renames; at no point does a half copy sit at `<appRoot>`. If the old folder cannot be moved, nothing changes and the person is told. Started directly from the Start-menu entry, the kept copy offers the same restore without a newer process to wait for, which covers an install folder an interrupted installer left unusable. Settings, About and updates offers **Return to <previous>** any time while a previous version is kept.
8. **Release notes**: `tools/release/notes.mjs` reads conventional commits from the previous `v*` tag (or the start of history) to `HEAD` and writes Markdown: breaking changes, New (`feat`), Fixed (`fix`), Faster (`perf`); other types are left out, duplicates merged, at most 60 lines per group. The main bundle embeds the notes of its version (`virtual:release-notes`, `update:notes`), shown under "What's new" in Settings, About and updates; the feed carries the notes of the offered version. Releases are tagged `v<version>` and built from a full clone.
9. **Version**: 0.7.0 from M7 (one minor per milestone), only in `apps/desktop/package.json`; installers are named `Stratlas-<version>-…`.

## Differential download: not used

electron-builder's blockmap path diffs the new installer against the previous installer cached by electron-updater, inside electron-updater's own download and install flow. With the own updater (needed for rollback and the JSON feed) that cache does not exist, and the app keeps the previous unpacked app, not an installer, so there is no old file to diff against. Re-implementing blockmap differencing (content-defined chunks, multi-range requests) for an opt-in channel on a 150 MB installer is not worth the code and the risk now; resuming an interrupted download covers the main cost of a poor connection, and offline sites update from a file anyway. electron-builder still writes `.blockmap` files, so a later differential step can be added without changing the feed format (an optional `blockmap` URL per file).

## Consequences

- One previous version uses about 400 MB in the app settings folder until the next update replaces it or a return to it makes it unnecessary.
- Rolling back does not touch projects or settings. Settings files from a newer version stay readable by the older one because `@aio/schema` changes are additive (unknown keys are dropped by zod objects).
- After a return the Windows "Apps" list still shows the newer version number until the next install; the files and shortcuts are the older version's.
- macOS installs from the DMG by hand; rollback there uses the same kept copy and restore but has had less testing than Windows (stream D4).
- An interrupted download, a refused signature or a failed copy leaves the installed version untouched.
